# 01 — Multi-language support (i18n)

**Status:** ◐ In progress (code complete 2026-10-06; native review pending)

## Goal

Support 7 locales — `pt-PT`, `pt-BR`, `en-GB` (default/fallback), `es`, `fr`,
`de`, `it` — across the whole UI, formatting and the Gemini output, with
automatic device-language detection and a manual override in Settings.

## Research & findings (2026-10-06)

- **Library options**:
  - `react-i18next` (+`i18next`): ~6–14 kB gz, biggest ecosystem, JSON
    catalogs, best known by coding agents.
  - Lingui: compile-time, ~2 kB core, needs macro/SWC plugin.
  - Paraglide: smallest, compile-time per-message functions.
  - react-intl/FormatJS: heaviest, best ICU support.
  - **Chosen: `i18next` + `react-i18next`** (ecosystem + agent familiarity),
    with catalogs **lazy-loaded per locale** via dynamic `import()` so the
    main bundle stays small (same principle as DECISIONS #12).
- **Detection**: the stock `i18next-browser-languagedetector` cannot express
  "pt-\* except BR → pt-PT", so we use a **custom resolver** (see Decisions).
- **Domain labels** are currently hardcoded PT in `calculations.ts`
  (`GOAL_LABELS`, `SEX_LABELS`, …), `mealTimes.ts` (slot labels,
  `WEEKDAY_LABELS`, `startsInLabel`), and `WorkoutBadge` is a literal union
  `'Pré-treino' | 'Pós-treino'`. All become **translation keys**; the badge
  type becomes `'pre' | 'post'` and is translated at render time.
- **LLM language**: prompt instructions and JSON-schema descriptions move to
  **English** (most robust for the model) with an explicit output-language
  block. Implemented in phase 1.4 together with Item 6 (single prompt
  refactor).
- Generator error messages become **error codes** translated by the UI —
  this also prepares the API boundary (Item 4).
- es/fr/de/it catalogs are agent-generated and flagged for native review.

## Decisions (also in docs/DECISIONS.md)

- 2026-10-06 — Library: `i18next` + `react-i18next`, lazy-loaded catalogs,
  typed keys (`CustomTypeOptions`), `en-GB` as source of truth. (DECISIONS #25)
- 2026-10-06 — Custom `resolveLocale`: exact locale match → language match
  (`pt-BR`→pt-BR; any other `pt-*`→pt-PT; `en-*`→en-GB; `es/fr/de/it-*`) →
  fallback `en-GB`. Override stored in `settings.locale` (`'auto' | Locale`),
  later persisted on the server profile. (DECISIONS #25)
- 2026-10-06 — Locale enters the plan `inputsHash`: changing the language
  marks the plan stale → user-confirmed regeneration (DECISIONS #6 preserved).
- 2026-10-06 — Supersedes DECISIONS #15 (UI only pt-PT).
